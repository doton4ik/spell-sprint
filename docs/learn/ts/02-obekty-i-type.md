# Урок 2. Объекты и `type`

Цель: читать описания данных (`type`) и понимать, как проект записывает «что это за штука и какие у неё поля».

## 2.1 Объект

**Объект** — набор именованных значений (полей):

```ts
const attempt = { word: 'inventory', isCorrect: false, tries: 2 }
attempt.word       // 'inventory'
attempt.tries      // 2
```

Поля читают через точку. Какого типа каждое поле, TypeScript выводит сам. Но когда объект создают много раз в разных
местах, форму описывают один раз и называют. Для этого есть ключевое слово `type`.

## 2.2 `type`: описание формы

Откройте `src/data/levelCheckBank.ts`:

```ts
export type LevelItem = {
  id: string
  skill: Skill
  level: 1 | 2 | 3 | 4
  prompt: string
  answer: string
  kind?: ItemKind
  choices?: string[]
  explain?: string
  ...
}
```

Так описан **один вопрос проверки уровня**. Читается как «вопрос — это объект с такими полями».

- Слева название поля, справа тип.
- `kind?: ItemKind` — вопросительный знак значит «поле можно не указывать». Без `?` поле **обязательно**:
  объект без `id` или `prompt` TypeScript не пропустит.
- `choices?: string[]` — тоже необязательное, и это **массив строк** (`string[]` читается «список строк», урок 3).
- `skill: Skill` — тип другого `type`. Типы можно собирать друг из друга.

Откройте любой файл, который создаёт такие вопросы, например `src/data/levelCheckDeep.ts`: каждый объект там
подчиняется `LevelItem`. Если забыть `prompt` или написать `levl: 2`, редактор подчеркнёт ошибку.

### Комментарии после полей

В проекте у многих полей есть пояснение после `//`:

```ts
id: string // stable: never derived from a position, so adding an item does not change the others' ids
```

Это комментарий: TypeScript его пропускает, он для людей. Привыкайте читать их: они объясняют **зачем** поле нужно.

## 2.3 Литеральные типы: набор разрешённых значений

В `LevelItem` есть странная строка:

```ts
level: 1 | 2 | 3 | 4
```

Тип поля `level` — не «любое число», а **только** 1, 2, 3 или 4. Значение 5 или 0 TypeScript не примет. Это называется
**литеральным типом**, а знак `|` соединяет варианты («или»).

То же со строками. Откройте `src/types/practice.ts`:

```ts
export type PracticeMode = 'write-en' | 'listen-write' | 'translate-ru' | 'choose-spelling' | 'fill-gap'
```

Режим практики — одна из пяти строк. Опечатка `'write-eng'` будет подчёркнута сразу, а не в тот момент, когда
пользователь откроет страницу.

Сравните с проектом без типов: ошибка в названии режима дала бы пустой экран у ученика. С типом вы узнаёте о ней
в редакторе.

## 2.4 Вложенные описания

Один `type` может содержать другой. Из того же файла:

```ts
export type PracticeAttempt = {
  id: string
  taskId: string
  topic: string
  userAnswer: string
  correctAnswer: string
  isCorrect: boolean
  attemptMode: PracticeMode
  ...
  createdAt: string
}
```

Так описана **одна запись из журнала ответов**: что спросили, что ответили, верно ли, в каком режиме. Приложение
сохраняет такие записи в `localStorage` и считает по ним статистику на главной (точность, серия, график недели).
Поле `attemptMode: PracticeMode` использует тип из 2.3.

## 2.5 Доступ к части типа

Как получить тип поля, не повторяя его? В проекте есть такая запись (файл `levelCheckBank.ts`):

```ts
const spellingLevels: Record<string, LevelItem['level']> = { ... }
```

`LevelItem['level']` читается «тип поля `level` у `LevelItem`». Это `1 | 2 | 3 | 4`. Если завтра добавят уровень 5,
изменится одна строка, а остальные типы поменяются сами. Идея: **одна правда в одном месте**.

## 2.6 `type` и `interface`

Вы можете встретить ещё слово `interface`, оно описывает почти то же самое. В проекте принято использовать `type`;
для начала достаточно знать, что `type` умеет всё то, что вы увидели.

## Вопросы на понимание

1. Что означает знак `?` в `kind?: ItemKind`? Что будет, если в `LevelItem` не указать `prompt`?
2. Чем `level: 1 | 2 | 3 | 4` лучше, чем `level: number`?
3. Какой тип у выражения `LevelItem['level']`? Зачем так записывают?
4. Что хранит `PracticeAttempt` и где в приложении используется (подсказка: главная страница и «Мои ошибки»)?
5. Почему опечатка в названии режима практики в типизированном проекте не доходит до ученика?
6. Если в `PracticeAttempt` добавить обязательное поле `reason: string`, что произойдёт с кодом, который создаёт
   такие записи? Это плюс или минус?
7. Придумайте тип `Round` для одного раунда Sprint: сколько слов угадано, сколько ошибок, дата. Какие поля обязательные?

1. `?` — поле необязательное, его можно не указывать (тогда значение `undefined`). Без `prompt` (обязательное поле)
   TypeScript выдаст ошибку «property 'prompt' is missing».
2. `number` разрешает любое число (5, −3, 0.5), а `1 | 2 | 3 | 4` — только четыре допустимых уровня. Неверное значение
   находится на этапе кода, а не в работе приложения.
3. `1 | 2 | 3 | 4`. Так тип не дублируют: изменив один `type`, меняют все места, где на него ссылаются.
4. Запись из журнала ответов: что спросили, что написал ученик, верно ли и в каком режиме. Статистика (точность,
   серия, график недели) и страница «Мои ошибки» строятся по таким записям.
5. Потому что строка не входит в `PracticeMode`, и TypeScript подчёркивает её при написании, а сборка (`pnpm check`)
   останавливается.
6. Везде, где создают `PracticeAttempt`, появится ошибка «не хватает поля `reason`». Это плюс: вы не забудете
   заполнить новое поле ни в одном месте. Если поле нужно не всегда, делают его необязательным (`reason?: string`).
7. Например: `type Round = { date: string; correct: number; misses: number }`. Все три обязательные (раунд без даты
   или счёта бессмыслен). В проекте такой тип есть: `SprintRound` в `src/services/sprint.ts`, в нём ещё список
   ответов `answers`.
