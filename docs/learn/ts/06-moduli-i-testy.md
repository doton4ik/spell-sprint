# Урок 6. Модули и тесты

Цель: понимать, как код разложен по файлам, как файлы друг друга подключают и как тесты доказывают, что
функции делают то, что вы думаете.

## 6.1 Модуль: один файл, одна тема

Каждый файл `.ts` — это **модуль**. Он может отдать наружу часть своего содержимого и взять нужное у других файлов.

**Отдать наружу** — `export`:

```ts
// src/services/contractions.ts
export const plain = (value: string) => …
export function expandWord(word: string): string[][] { … }
export function sameText(a: string, b: string) { … }
const MAX_VARIANTS = 32      // без export: виден только внутри файла
```

Всё без `export` остаётся «приватным» для файла. Так файл скрывает вспомогательные детали и показывает только то, что
нужно остальным (в `contractions.ts` приватные `IRREGULAR`, `NUMBER_WORDS`, `MAX_VARIANTS`).

**Взять** — `import`:

```ts
// src/services/levelCheck.ts
import { plain, sameText } from './contractions'
import type { LevelItem } from '../data/levelCheckBank'
```

- Фигурные скобки перечисляют, что нужно из модуля.
- `'./contractions'` — путь: `./` значит «в той же папке», `../` — «на уровень выше». Расширение не пишут.
- `import type` — подключает только типы. Они исчезают при сборке и в готовом приложении их нет.

## 6.2 Как устроен `src`

Папки проекта (смотрите карту в `CLAUDE.md`) разделяют обязанности:

| Папка | Что в ней | Правило |
|---|---|---|
| `src/data/` | содержимое: слова, правила, тексты, вопросы | данные, почти без логики |
| `src/types/` | описания типов | только типы |
| `src/services/` | логика: подсчёты, хранение, проверки | не знает про экран |
| `src/components/` | кусочки интерфейса | показывают данные |
| `src/pages/` | целые страницы | собирают компоненты |

Важное правило направления: **страницы знают про сервисы, а сервисы про страницы ничего не знают**. Поэтому
`contractions.ts` можно проверить тестом без браузера и без React: ему нужна только строка на входе.

Поток данных, например для строки «серия дней» на главной:

```
localStorage → practiceStorage.ts (читает записи) → dailyPlan.ts: getStreak() → DashboardPage.tsx (рисует число)
```

## 6.3 Чистые функции

Функция называется **чистой**, если:

1. результат зависит только от аргументов;
2. она ничего не меняет снаружи (не пишет в хранилище, не меняет переданные данные).

`plain`, `sameText`, `isCorrectAnswer`, `diffWords` чистые: одинаковый вход всегда даёт одинаковый результат. Такие
функции легко тестировать и можно смело переиспользовать. Функции, которые читают `localStorage` или текущее время
(`getStreak` читает журнал ответов), чистыми не являются, поэтому в проекте они принимают данные необязательным
аргументом: `getStreak(attempts = getPracticeAttempts())`. В тесте можно передать свои данные вместо реальных.

## 6.4 Тесты

Тест — маленькая программа, которая вызывает вашу функцию и проверяет ответ. Проект использует **Vitest**. Откройте
`src/services/contractions.test.ts`:

```ts
import { describe, expect, it } from 'vitest'
import { sameText } from './contractions'

describe('contractions', () => {
  it('does not mix up words that only look alike', () => {
    expect(sameText('Its tail is long', "It's tail is long")).toBe(false)
    expect(sameText('I cant swim', "I can't swim")).toBe(false)
  })
})
```

- `describe('название группы', () => { … })` — группа тестов.
- `it('что должно быть верно', () => { … })` — один тест. Читается как предложение: «it (оно) does not mix up…».
- `expect(значение).toBe(ожидание)` — утверждение: «я ожидаю, что значение равно ожиданию». Если нет, тест
  падает и пишет, что ожидали и что получили.

Запуск (в папке проекта):

```bash
pnpm test
```

Видно список файлов и «Tests 147 passed». Если вы меняете `contractions.ts` и ломаете логику, нужный тест покраснеет.

### Зачем тесты в этом проекте

Вы сами проверяли, что «It's very cold» должно считаться верным для «It is very cold». Раньше так не работало.
Поэтому для **каждой** такой ситуации в тесте записаны пары: «эти две фразы одинаковые», «эти — разные» (`its` ≠ `it's`).
Тест — это **память проекта**: когда вы поймали ошибку, фиксируете её тестом, и она не вернётся незамеченной.

Хорошие тесты проверяют три группы случаев:

1. **Обычные** (всё как надо): `It's` = `It is`.
2. **Граничные** (края): пустая строка, одно слово, число 20 и 21.
3. **«Похожее, но неверное»**: `its` ≠ `it's`, `3 cats` ≠ `two cats`.

## 6.5 Что запускает `pnpm check`

Из `package.json`:

```
check = typecheck && lint && format:check && test && check:library && check:pairs && check:classifier && check:proofreading && check:rules
```

Знак `&&` значит «если предыдущее прошло, запускай следующее».

| Шаг | Что проверяет |
|---|---|
| `typecheck` | `tsc -b`: типы (уроки 1–5) |
| `lint` | `oxlint`: подозрительный код (неиспользуемые переменные и тому подобное) |
| `format:check` | `prettier`: единый вид кода (пробелы, кавычки) |
| `test` | Vitest: ваши тесты |
| `check:*` | проверки содержимого: слова, пары, тексты вычитки, правила |

Эти проверки вместе дают уверенность: если всё зелёное, приложение собирается, логика даёт ожидаемые ответы, а в
контенте нет явных ошибок. Поэтому в `CLAUDE.md` написано: «перед "готово" `pnpm check` должен пройти».

8. Добавить тест на этот случай (и на похожие «неверные»), чтобы при будущих изменениях ошибка не вернулась молча.
