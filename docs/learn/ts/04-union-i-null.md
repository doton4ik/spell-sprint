# Урок 4. «Или» в типах, `null` и проверки

Цель: понимать самый важный механизм TypeScript. Значение может быть одного из нескольких видов, а перед
использованием код проверяет, какого именно. Это защищает от ошибок вроде «cannot read property of undefined».

## 4.1 Union: «этот тип или тот»

Знак `|` в типе читается «или». Это называется **union** (объединение).

```ts
let id: string | number
id = 'abc'    // можно
id = 42       // можно
id = true     // ошибка
```

Вы уже встречали такое: `value: Date | string` (урок 1), `1 | 2 | 3 | 4` (урок 2). Особо частый случай — «значение
или ничего»:

```ts
number | null          // число или null
string | undefined     // строка или undefined
```

`null` и `undefined` значат «значения нет». У нас в проекте: `percent` вернёт число или `null`; необязательное поле
`explain?: string` имеет тип `string | undefined`.

## 4.2 Почему нельзя сразу использовать

```ts
function show(x: string | null) {
  return x.toUpperCase()    // ошибка: 'x' is possibly 'null'
}
```

TypeScript не знает, что внутри, и не позволяет вызвать метод строки у значения, которое может быть `null`. Это защита от
реальной ошибки: `null.toUpperCase()` в браузере роняет страницу.

## 4.3 Сужение (narrowing)

Решение — **проверить**. После проверки TypeScript понимает, что внутри условия значение другого типа:

```ts
function show(x: string | null) {
  if (x === null) return 'нет значения'
  return x.toUpperCase()          // здесь x уже точно string
}
```

Откройте `src/services/dateKeys.ts` из урока 1:

```ts
const date = typeof value === 'string' ? new Date(value) : value
```

`value` — это `Date | string`. Проверка `typeof value === 'string'` сужает: в ветке «да» это строка (её превращают в
`Date`), в ветке «нет» TypeScript знает, что это `Date`. Поэтому после строки переменная `date` точно `Date`, и методы
`getFullYear()` и другие доступны.

Основные способы сужения:

| Проверка | Для чего |
|---|---|
| `typeof x === 'string'` | примитивы (`string`, `number`, `boolean`) |
| `x === null`, `x === undefined`, `if (x)` | отсутствие значения |
| `x === 'choice'` | конкретное значение из литерального типа |
| `Array.isArray(x)` | массив ли это |
| `'field' in obj` | есть ли поле в объекте |

### Пример: проверка ответа

`src/services/levelCheck.ts`:

```ts
export function isCorrectAnswer(item: LevelItem, answer: string) {
  if (item.kind === 'choice') return normaliseAnswer(answer) === normaliseAnswer(item.answer)
  return item.answer.split('|').some((option) => sameText(option, answer))
}
```

У вопроса `kind` необязательное и может быть `'type' | 'choice' | 'dictation' | undefined`. Для выбора из вариантов ответ
сравнивается точно, для остальных (печатных) допускаются несколько вариантов, разделённых `|`, и проверка идёт через
`sameText` (урок 6), которая знает про сокращения («It's» = «It is»).

### Пример: проверка внешних данных

`src/services/rulesService.ts`:

```ts
function cachedLinks(): RuleWordLink[] {
  try {
    const value = JSON.parse(window.localStorage.getItem(LINKS_CACHE_KEY) ?? '[]')
    return Array.isArray(value) ? value : []
  } catch {
    return []
  }
}
```

`JSON.parse` возвращает неизвестно что. Поэтому код проверяет `Array.isArray(value)`, и если там не массив (повреждённые
данные), возвращает пустой список. Так приложение не падает от плохих данных (подробнее в уроке 8).

## 4.4 `?.` и `??`: безопасный доступ

Два короткие оператора, которые вы будете видеть постоянно.

**`?.` (необязательная цепочка)**: «если слева есть значение, возьми поле, иначе `undefined`, и не падай».

```ts
result.skills[skill]?.ability     // если для этого навыка нет результата, то undefined
```

**`??` (значение по умолчанию)**: «если слева `null` или `undefined`, возьми то, что справа».

```ts
result.skills[skill]?.ability ?? 0
```

Это строка из `abilityChange` в `levelCheck.ts`: возьми «способность» по навыку, а если навык не измерялся, то ноль.
Старые проверки уровня содержали три навыка, новые пять, поэтому поле может отсутствовать, и код это учитывает.

Не путайте `??` и `||`: `||` срабатывает ещё и на `0`, `''`, `false`. Для `0 ?? 5` получится `0`, а для `0 || 5` — `5`.

## 4.5 Восклицательный знак `!`

В `src/pages/MistakesPage.tsx` есть такая строка:

```tsx
{entry.pairId ? (
  <button onClick={() => openPairOnPairsPage(entry.pairId!)}>…</button>
) : …}
```

`pairId` необязательный (`string | undefined`). Условие выше уже проверило его наличие, но внутри функции-обработчика
TypeScript этого «не помнит» и считает, что значение может исчезнуть. `!` говорит ему: «поверь, здесь значение
точно есть». Используйте `!` только когда вы **сами уверены** в проверке: если ошибиться, он молча пропустит `undefined`.

## 4.6 Свой фильтр типа

В том же файле:

```ts
const wordIds = [...new Set(entries.map((entry) => entry.wordId).filter((id): id is string => Boolean(id)))]
```

`entries.map(entry => entry.wordId)` даёт список `(string | undefined)[]`. Обычный `filter(Boolean)` убрал бы пустые
значения, но TypeScript всё равно считал бы тип списка прежним. Запись `(id): id is string => Boolean(id)` сообщает:
«если функция вернула `true`, то `id` точно строка». Тогда итог получает тип `string[]`. Это называется **type guard**.

## Попробуйте сами

```ts
type Level = 'A2' | 'B1' | 'B2' | 'C1'

function label(level: Level | null) {
  // верните 'не определён', если level равен null, иначе 'Уровень ' + level
}
```

1. Допишите функцию так, чтобы не было ошибок типов.
2. Измените `Level | null` на `Level | undefined` — что поменялось в проверке?
3. Напишите `function pick(a?: number, b?: number)`, которая возвращает `a ?? b ?? 0`. Проверьте `pick()`,
   `pick(0)`, `pick(undefined, 5)`.

## Вопросы на понимание

1. Что значит запись `string | null` и почему нельзя сразу вызвать у такого значения `.toUpperCase()`?
2. Что такое сужение типа? Приведите пример из `localDayKey`.
3. Как `isCorrectAnswer` решает, как проверять ответ? Что произойдёт для вопроса без поля `kind`?
4. Что делает `result.skills[skill]?.ability ?? 0` и почему здесь нужны оба оператора?
5. Чем `0 ?? 5` отличается от `0 || 5`? Для какого значения это важно, если мы считаем очки?
6. Зачем `cachedLinks` проверяет `Array.isArray(value)`, хотя функция вроде бы всегда получает массив?
7. Когда безопасно писать `entry.pairId!`, а когда нет?
8. Для чего записывают `(id): id is string => Boolean(id)`, если можно просто `filter(Boolean)`?

<summary>Ответы (откройте после своих)</summary>

1. «Строка или `null`». Если значение `null`, у него нет методов строки, и вызов упал бы в работе приложения.
   TypeScript заставляет сначала проверить.
2. Сужение — это когда после проверки TypeScript знает более точный тип. В `localDayKey` значение `Date | string`;
   проверка `typeof value === 'string'` делает его строкой в одной ветке и `Date` в другой.
3. Для `kind === 'choice'` ответ сравнивается точно. Для всего остального (печатный ответ, диктант) допускаются
   варианты через `|` и проверка `sameText`. У вопроса без `kind` значение `undefined`, проверка `=== 'choice'` ложна,
   и он проверяется как печатный.
4. `?.` не даёт упасть, если результата по навыку нет (получается `undefined`), а `??` заменяет `undefined` нулём,
   чтобы дальше считать среднее. Только `?.` оставил бы `undefined`, а только `??` не защитил бы от обращения к
   несуществующему полю.
5. `0 ?? 5` даёт `0`, `0 || 5` даёт `5`. `||` считает `0` «пустым». Для очков, где `0` — настоящее значение, нужен `??`.
6. Данные приходят из `localStorage` через `JSON.parse`, TypeScript про них ничего не знает, а пользователь или
   другая версия приложения могли записать что угодно. Проверка защищает от падения.
7. Безопасно, если вы только что проверили наличие значения и между проверкой и использованием оно не может исчезнуть.
   Небезопасно как способ «заставить замолчать» ошибку без проверки: если значения нет, получите сбой в работе.
8. `filter(Boolean)` убирает пустые значения, но TypeScript не понимает этого и оставляет тип `(string | undefined)[]`.
   Type guard сообщает, что после фильтра остались только строки, и тип становится `string[]`.
