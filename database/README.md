# Database (Supabase)

All SQL is run by hand in the Supabase SQL Editor (project **SpellSprint**). Every file is written to be
safe to run again (`if not exists`, `on conflict do nothing`) and never deletes data.

`rules-import/` holds CSV exports of the rules tables (reference only, not run).

## Adding a change

1. Create a new file with the next number in the name, e.g. `13-something.sql`, and describe at the top
   what it does, that it keeps data, and how to undo it.
2. Wrap it in `begin; … commit;` so a failure changes nothing.
3. Run it in the SQL Editor, then add a row to the table above.
4. If tables or columns changed, regenerate `src/types/database.ts`
   (`npx supabase gen types typescript --project-id <id>`) so the app's types match.

## Rules of thumb

- Every table with user data has RLS with `user_id = auth.uid()`; public reference tables are read-only.
- Never use the `service_role` key in the app. The app only has the public anon key.
- Check after a change: Supabase → Advisors → Security should show no errors.

## Offline copy of the built-in rules

`src/data/builtInRules.json` is a copy of the public built-in rules and their examples (exported
2026-10-08). The app uses it when Supabase cannot be reached, so the Rules page works offline. If the
built-in rules or examples change in the database, export them again (read-only `select` of
`rules` where `source = 'built-in' and visibility = 'public'`, plus their `rule_examples`) and
replace the file.

The articles pack is the exception to "export from the database": it is built from one source file,
`rules-import/articles-pack.json`, by `node scripts/build-articles-pack.mjs`, which writes the SQL file, adds the
rules and examples to `builtInRules.json` and writes `src/data/builtInRuleExercises.json` (the exercises, offline).
The app uses those bundled exercises only for a rule the database has none for, so nothing shows twice once the SQL
is run. After running the SQL, nothing else needs to be done in the app.
